# Приложение для анкетирования студентов

## User

Это сущность пользователя
У него есть несколько ролей
![[..\src\Domain\User\UserRole.cs]]

Где:

- **Admin** - чел, что заведует всем
- **DeputyHead** - чел, что заведует кафедрой
- **StudentGroup** - группа студентов
- **Employer** - человек, что представляет собой компанию, куда идут студенты
- **Staff** - работники

`\\ User.cs`
![[..\src\Domain\User\User.cs]]

Так как нету изначальной базы данных, админ все сам заполняет. Для этого есть отдельные поля

`User` - универсальная учетная запись для нескольких сценариев:

- админ
- группа студентов
- сотрудник
- представитель работодателя

Из-за этого в сущности есть nullable-поля, которые зависят от роли:

- `DepartmentId` нужен, когда пользователь привязан к кафедре
- `GroupId` нужен для студенческой группы
- `TeacherId` нужен, если учетная запись связана с преподавателем
- `OrganizationName` нужен для работодателей

Создание пользователя идет не через один общий конструктор, а через явные фабричные методы:

- `CreateGroupUser(...)`
- `CreateStaff(...)`
- `CreateAdmin(...)`

## Что вообще за система

Это сервис анкетирования для колледжа. В центре модели не пользователи сами по себе, а процесс сбора анкет и контекста, в котором анкета была заполнена.

Основные сценарии:

- админ заводит справочники
- админ создает формы анкет
- пользователь с нужной ролью входит в систему
- пользователь отправляет `Submission` по выбранной форме
- потом по данным строятся отчеты

## Слои решения

Проект разделен довольно стандартно по слоям:

- `src/Domain` - предметная область, сущности, aggregate root, value objects, бизнес-правила
- `src/Application` - use case'ы: команды, запросы, хендлеры, валидация
- `src/Infrastructure` - EF Core, БД, авторизация, генерация отчетов, импортеры
- `src/Web.Api` - HTTP endpoints и composition root
- `src/Web.Client` - фронтенд
- `src/SharedKernel` - базовые абстракции и общие типы вроде `Entity`, `AggregateRoot`, `Result`

## SharedKernel

В `SharedKernel` лежат базовые доменные асбтракции:

- `Entity` - базовая сущность с `Id`
- `AggregateRoot` - сущность верхнего уровня, которая еще умеет копить domain events
- `Result` - единый способ возвращать успех/ошибку без исключений как основной ветки логики
- `ISoftDeletable` - пометка, что сущность удаляется мягко через `IsDeleted`

Почти весь домен написан в стиле:

- проверить входные данные
- вернуть `Result.Failure(...)`, если что-то не так
- иначе создать/обновить объект и вернуть `Result.Success(...)`

## Справочники колледжа

Помимо пользователей в домене есть отдельные сущности справочников колледжа:

- `Department`
- `Discipline`
- `Teacher`
- `Speciality`
- `Specialization`

Используются как контекст анкеты и как фильтры отчетов.

Связи между ними:

- `Discipline` хранит `DepartmentId`
- `Teacher` хранит `DepartmentId`
- `Specialization` хранит `SpecialityId`

То есть это часть доменной модели, на которую завязаны анкеты и аналитика.

## Формы анкет

формы и вопросы

- `Form` - aggregate root анкеты
- `Question` - сущность внутри формы
- `QuestionType` - тип вопроса
- `FilterField` - какие поля контекста обязательны для заполнения формы

У `Form` есть:

- `Title`
- `IsActive`
- `RequiredFilters`
- коллекция `Questions`

Что важно по поведению:

- вопрос добавляется через `AddQuestion(...)`
- порядок вопросов контролируется в домене
- форма может быть активна или деактивирована
- типы вопросов захардкожены enum'ом

![[..\src\Domain\Questionnaires\FormAggregate\QuestionType.cs]]

Из `QuestionType` видно, что система поддерживает не только текст и число, но и рейтинги, включая `WeightedRating`.

## Submission и Answer

Главная операционная сущность системы - это `Submission`, то есть факт отправки анкеты.

Внутри:

- `FormId`
- `UserId`
- `SubmittedAt`
- `DeviceId`
- `Context`
- коллекция `Answers`

`SubmissionContext` нужен, чтобы сохранить, в каком контексте проходилось анкетирование. Например:

- по какой дисциплине
- по какому преподавателю
- по какой кафедре
- по какой специальности / специализации
- от какой организации

Форма и сами ответы живут отдельно от справочников, но submission сохраняет ссылки на нужный контекст на момент прохождения.

`Answer` хранит:

- ссылку на `Question`
- строковое значение
- числовое значение
- вес

Домен сразу валидирует:

- нельзя добавить два ответа на один и тот же вопрос в рамках одного `Submission`
- ответ должен иметь либо `Value`, либо `NumericValue`
- числовые значения ограничены диапазоном
- для _weighted rating_ оценка не должна превышать вес

## Доменные сервисы

Кроме сущностей есть еще доменный сервис `ScoreCalculator`.

Он считает средний балл по ответам:

- для обычных числовых ответов - обычное среднее
- для `WeightedRating` - нормализованное среднее с учетом веса

## Как проходит запрос через систему

Общий путь запроса примерно такой:

1. HTTP endpoint в `Web.Api` принимает запрос
2. endpoint вызывает command или query из `Application`
3. handler работает через абстракции вроде `IRepository<>` и `IApplicationDbContext`
4. handler создает или меняет доменные сущности
5. `Infrastructure` сохраняет изменения через EF Core

## Application слой

В `Application` почти все разложено по фичам:

- `Users`
- `Forms`
- `Submissions`
- `Departments`
- `Disciplines`
- `Teachers`
- `Reports`

Внутри обычно лежит набор:

- `Command` или `Query`
- `Handler`
- иногда `Validator`
- DTO ответа

Регистрация происходит автоматически через `services.Scan(...)`, а сверху навешиваются декораторы:

- `ValidationDecorator`
- `LoggingDecorator`

То есть перед тем как handler реально выполнится:

- команда может провалидироваться через FluentValidation
- запрос или команда логируются

## Infrastructure слой

`Infrastructure` отвечает за техническую реализацию абстракций приложения.

Что тут важно:

- `ApplicationDbContext` - EF Core контекст
- `Repository<>` - generic repository
- конфигурации сущностей по папкам aggregate'ов
- `TokenProvider`, `PasswordHasher`, `UserContext` - auth
- `WordReportGenerator` - генерация отчетов
- `DbInitializer` - начальное заполнение

База данных - PostgreSQL.s

## Web.Api

`Web.Api` - это точка входа.

В `Program.cs` можно увидеть, как собирается приложение:

- подключается `AddApplication()`
- подключается `AddPresentation()`
- подключается `AddInfrastructure(...)`
- мапятся endpoints
- включаются authentication / authorization
- при старте применяются миграции
- после миграций запускается `DbInitializer`

## Опасненько

- `User` совмещает несколько видов учеток, поэтому не все поля обязательны всегда
- часть связей хранится просто через `Guid`, без навигационных свойств
- `SubmissionContext` несет много бизнес-смысла, хотя выглядит как простой record
- доменные правила частично сидят в сущностях, а частично в application validators
- soft delete используется в нескольких сущностях, так что "удаление" не всегда физическое

## Коротко

Если совсем в одном абзаце, то проект устроен так:

админ наполняет справочники и создает формы, пользователи разных ролей проходят анкетирование, система сохраняет `Submission` с ответами и контекстом, а потом строит аналитику и отчеты на базе этих данных.
