# Endpoints

## Purpose
All HTTP routes for the active API, implemented as minimal-API handlers — one small `internal sealed class` per operation implementing `Web.Api.Endpoints.IEndpoint` (`void MapEndpoint(IEndpointRouteBuilder app)`). Classes are auto-discovered by reflection in `Extensions/EndpointExtensions.cs` (`AddEndpoints(Assembly)`), so adding a new `IEndpoint` file is the only step needed to wire up a new route — nothing to register manually in `Program.cs`. Every handler follows the same shape: bind a request/route param, resolve an `Application`-layer `ICommandHandler<TCommand[, TResponse]>` or `IQueryHandler<TQuery, TResponse>` from DI, call `Handle(...)`, and convert the resulting `SharedKernel.Result`/`Result<T>` to an `IResult` via `.Match(Results.Ok, CustomResults.Problem)` or an explicit `if (result.IsFailure) return CustomResults.Problem(result);` + success branch. `IEndpoint.cs` (the marker interface) and `Tags.cs` (Swagger tag constants — only partially used, see caveats below) live directly in this folder, alongside the 10 feature subfolders.

## Key Files
| File | Description |
|------|-------------|
| `IEndpoint.cs` | Marker interface every endpoint class implements: `void MapEndpoint(IEndpointRouteBuilder app)`. |
| `Tags.cs` | `static class Tags` with `const string` Swagger group names: `Users`, `Submissions`, `Forms`, `Departments`, `Teachers`, `Settings`. Incomplete — many endpoints use raw string literals (`"Dictionaries"`, `"Reports"`, `"Teachers"`) instead of this class; don't assume every `WithTags(...)` call references it. |

## For AI Agents
### Working In This Directory
- To add a new endpoint: create a new `internal sealed class : IEndpoint` file under the matching feature folder (or a new folder for a new feature group), implement `MapEndpoint`, call the matching `Application` layer handler, and set `.WithTags(...)` + an explicit auth call (`.RequireAuthorization()`, `.HasPermission(Permissions.X)`, or `.AllowAnonymous()`). Reflection-based discovery in `../Extensions/EndpointExtensions.cs` handles registration automatically — there is no central route table to edit.
- Mirror the naming convention already in place: file name == class name == the CRUD verb (`Create`, `Update`, `Delete`, `Restore`, `GetById`, `GetList`), namespaced `Web.Api.Endpoints.<FeatureGroup>`. Several `Create`/`Delete`/etc. classes across different folders share the same short name (`Departments.Create` vs `Teachers.Create`) — this is intentional and only works because each lives in its own namespace; don't flatten folders or you'll get compile collisions.
- Soft-delete resources (`Departments`, `Disciplines`, `Specialities`, `Specializations`, `Teachers`) consistently expose `DELETE .../{id:guid}` + `POST .../{id:guid}/restore` as a pair — if you add a new soft-deletable dictionary type, follow this exact two-endpoint shape rather than inventing a different one.
- Watch the `Reports/` naming trap: `GetAnalyticsByPeriod` (singular) and `GetAnalyticsByPeriods` (plural) are different routes/handlers for different aggregation granularities — don't assume one is a typo of the other or collapse them.
- Body-bound vs query-string-bound `GET`/query endpoints are inconsistent across groups: `Dictionaries/*` and `Forms/GetList` take no parameters; `Reports/GetAnalyticsBy*` use `POST` with a JSON body even though they're logically reads; `Submissions/GetList` uses `[AsParameters]` query-string binding on a `GET`. When adding a new list/filter endpoint, pick whichever matches the sibling endpoint it's most structurally similar to, not a blanket rule.
- The `"Dictionaries"` Swagger tag is overloaded — it's used by `Departments`, `Disciplines`, `Specialities`, `Specializations` (all genuinely dictionary/lookup CRUD) but also, seemingly by mistake, by `Teachers/Restore.cs` (every other `Teachers/*` file uses `"Teachers"`). If touching `Teachers/Restore.cs`, consider fixing the tag to `"Teachers"` for consistency, but confirm with the user first since it changes the Swagger grouping.
- Permission checks are the security boundary here — there is no other authorization layer in front of these routes. When copying an existing endpoint as a template for a new one, always double check the auth call was copied and is correct for the new operation (e.g. don't accidentally leave `.AllowAnonymous()` from `Login.cs`, or drop the auth call entirely).

## Dependencies
### Internal
- `Application` — every endpoint's actual logic is a call into an `ICommandHandler`/`IQueryHandler` here (e.g. `Application.Users.SignIn.LoginUserCommand`, `Application.Departments.Create.CreateDepartmentCommand`, `Application.Reports.Queries.GetAnalyticsByPeriod.GetAnalyticsByPeriodQuery`).
- `SharedKernel` — `Result`/`Result<T>` (return type of every handler call) and `Permissions` (string constants for `.HasPermission(...)`/`RequireAuthorization(...)`).
- `Web.Api.Extensions` — `ResultExtensions.Match`, `EndpointExtensions.HasPermission`.
- `Web.Api.Infrastructure` — `CustomResults.Problem(Result)` for the failure branch of nearly every endpoint.
- Cross-references within `Endpoints/`: several files `using Web.Api.Endpoints.Users;` purely to get the `Permissions` extension method's containing namespace resolved via that import chain (harmless but slightly odd — it's not actually calling into `Users/`-specific types).

### External
- ASP.NET Core minimal APIs (`Microsoft.AspNetCore.Routing`, `IEndpointRouteBuilder`, `Results`).
- `Domain.User` (`UserRole` enum, referenced directly by `Users/CreateStaff.cs`'s request record).
