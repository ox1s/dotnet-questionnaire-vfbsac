# tests/

## Purpose
Automated test suites for the ACTIVE backend stack only (`src/Domain`, `src/Application`, `src/Infrastructure`, `src/Web.Api`, `src/SharedKernel`). This directory does NOT test the legacy `Questionnaire.*` projects (`src/Questionnaire.Api`, `Questionnaire.Application`, `Questionnaire.Domain`, `Questionnaire.Infrastructure`, `Questionnaire.Contracts`, `Questionnaire.SharedKernel`) — those have no test coverage under `tests/`. Two xUnit projects live here: `ArchitectureTests` (Clean Architecture layering rules, enforced via NetArchTest) and `Application.UnitTests` (scaffolded for Application-layer unit tests, but currently contains no test classes).

## For AI Agents
### Working In This Directory
- **`ArchitectureTests/Layers/LayerTests.cs` currently enforces exactly six rules**, all one-directional (no rule prevents Presentation/Infrastructure from depending inward, which is expected and correct for Clean Architecture):
  1. `Domain_Should_NotHaveDependencyOnApplication` — Domain must not reference the Application assembly (by string name "Application").
  2. `DomainLayer_ShouldNotHaveDependencyOn_InfrastructureLayer`
  3. `DomainLayer_ShouldNotHaveDependencyOn_PresentationLayer`
  4. `ApplicationLayer_ShouldNotHaveDependencyOn_InfrastructureLayer`
  5. `ApplicationLayer_ShouldNotHaveDependencyOn_PresentationLayer`
  6. `InfrastructureLayer_ShouldNotHaveDependencyOn_PresentationLayer`
  - There is no rule checking `SharedKernel` (e.g. nothing stops Domain from being forced to depend on it in the wrong direction) — if you add a `SharedKernel` layering rule, add both a positive assertion and a test, following the existing `Types.InAssembly(...).Should().NotHaveDependencyOn(...)` pattern.
  - If you split a layer further (e.g. move a subfolder of Application into its own assembly), update `BaseTest.cs`'s assembly-resolving marker types first — the tests key off assembly identity via a representative type, not project names.
- **`Application.UnitTests` is an empty scaffold** — it has a `.csproj` and `GlobalUsings.cs` only, no test classes. Do not assume any Application-layer behavior (validators, command/query handlers, pipeline behaviors) is currently covered by automated tests. If asked to "run the unit tests" or "check test coverage" for Application, be explicit that this project builds but has zero test cases today.
- Both projects target `net10.0` and use xUnit + Shouldly (not FluentAssertions) for assertions — match that style if adding tests (`result.ShouldBeTrue()`, not `result.Should().BeTrue()`).
- `obj/` and `bin/` under both projects are build output (including a full copy of `Web.Api`'s runtime dependencies under `ArchitectureTests/bin/Debug/net10.0/`, pulled in because `ArchitectureTests` references `Web.Api` directly) — never edit or read these for logic; they're regenerated by `dotnet build`/`dotnet test`.
- `*.csproj.lscache` files in both projects are IDE/build cache artifacts, not build inputs.
